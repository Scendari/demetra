Ce que cette page permet de vérifier

Les schémas décrivent le comportement de référence soumis à ta validation. Les TNR doivent comparer le moteur à ces règles, jamais modifier les attendus pour obtenir des tests verts. Un écart connu reste un échec du test ; le succès d’un banc isolé ne le corrige pas. Cette page ne lance pas de véritable Workflow. Les étapes montrent les moments importants ; certains lancements et résultats peuvent être regroupés dans une même étape. En exécution réelle, les durées et l’ordre des événements peuvent varier.

Évolution proposée · cas 99 à 133 : la famille « Évolution · désactivation » présente des règles à valider, non implémentées et non testées. L’option envisagée est self.deactivate_tasks(["a"], propagate=False) ; propagate=True reste la valeur proposée par défaut. Les anciens cas restent la référence du moteur actuel : pour une désactivation dynamique, leur DEACTIVATED s’accompagne d’une propagation, contrairement au nouveau sens proposé. Les avis existants sont conservés ; les nouvelles propositions ont leurs propres avis.

Les anciens cas 57 et 58 ont été retirés : ils reposaient sur une exception interceptée volontairement par un test, sans parcours utilisateur normal démontré. Les autres numéros sont conservés. Les éventuels avis sur ces cas restent sauvegardés et inclus dans l’export JSON.

Le cas 74 a également été retiré : il supposait une Task déjà annulée alors que l’ordonnanceur continuait, sans parcours utilisateur normal démontré. Son test technique est conservé, ainsi que les éventuels avis enregistrés et leur export JSON.

Le cas 75 a été retiré pour la même raison : le test impose une Task annulée et une autre réussie, sans démontrer un blocage du Workflow sur un run normal. Le test et les éventuels avis restent conservés.

Il existe une infinité de graphes possibles. Ce catalogue couvre les principales situations prévues par le code : dépendances, places d’exécution, erreurs, stop_on_error, always_run, ignore_on_error, désactivation et finalisation. Les cas 83 à 98 ajoutent les contrôles de cycle de vie, les boucles sans Step actif, les scripts, un prérequis entre Steps et la finalisation d’une erreur de Step ignorée. Ils ne constituent pas un catalogue exhaustif des requêtes SQL, plugins ou commandes ciblées telles que run-task.

Chaque cas porte un niveau principal : Workflow, Task, Itération ou Step. Le filtre « Niveau » isole ce niveau ; le tri « Workflow → Task → Itération → Step » regroupe les tuiles dans cet ordre. Une tuile peut aussi montrer les conséquences sur d’autres niveaux, sans être classée plusieurs fois. Les flèches représentent toujours des prérequis, jamais un lien parent-enfant.

Un banc impose un état ou isole des opérations externes : son succès ne garantit pas qu’une configuration soit acceptée par la commande run. Chaque nœud indique son niveau. Une Task affiche ses options ; les valeurs absentes du schéma sont active: true et ignore_on_error: false. Une Itération ou un Step affiche son contexte, sans option always_run de Task. Un statut coloré n’est pas une validation métier. Les cas sensibles sont signalés séparément.

Probabilité estimée de rencontrer la situation décrite : 1 · Très rare (situation exceptionnelle ou course entre exécutions), 2 · Faible (situation occasionnelle, option ou erreur particulière), 3 · Commun (situation usuelle de dépendances, de capacité ou de gestion d’un KO). Cette échelle est une appréciation qualitative, sans statistiques de vos runs. Elle ne mesure ni la gravité, ni la probabilité de réussite du test. « Commun » ne signifie pas que les erreurs surviennent souvent ; les états ciblés ne sont pas tous des parcours ordinaires.

Quelques repères pour lire les cas
  • Task ordinaire : Task avec always_run: false. Elle attend que tous ses prérequis aient terminé avec succès, avec un avertissement ou avec une erreur explicitement ignorée.
  • Prérequis direct ou indirect : dans A → B → C, C dépend directement de B et indirectement de A. A est aussi appelée un ancêtre de C.
  • Désactivation et always_run : la désactivation atteint les descendantes ordinaires encore en attente, même à travers une Task always_run. Dans A → C → B, si A est désactivée, C avec always_run: true peut s’exécuter ; B reste désactivée, sauf si B porte aussi cette option. Une Task déjà lancée ou réservée est préservée.
  • Place d’exécution : max_threads_tasks: 2 autorise au maximum deux Tasks à travailler en même temps. Une Task sans prérequis peut donc devoir attendre une place.
  • Lancement réservé : Lancelot a choisi la Task et prépare son démarrage. Même si elle affiche encore WAITING, elle n’est plus disponible pour un autre lancement ou une désactivation directe.
  • Thread : exécution Python dédiée à une Task. Son démarrage et sa fin complète peuvent être légèrement décalés par rapport à l’affichage du statut de la Task.
  • Statut de fin : la Task n’est plus en attente ni en cours. Cela inclut la réussite, l’échec, l’avertissement, la désactivation, l’annulation et le blocage. Cela ne signifie donc pas forcément qu’elle a été exécutée.
  • Nettoyage et finalisation : une Task nommée cleanup représente un nettoyage déclaré dans le Workflow. Elle ne remplace pas les opérations automatiques de fin du Workflow : attente des exécutions, suppression des ressources temporaires, bilan, audit et logs.

Dans un cas de type « Configuration », NON_DÉMARRÉ et CONTRÔLE_KO sont des repères de lecture : aucun run n’a commencé. Dans un « État ciblé », les statuts de départ sont choisis pour examiner une règle ; l’exemple ne garantit pas qu’un run ordinaire atteindra ces états.

Lancelot vérifie d’abord que la Task est active et n’a pas déjà de lancement engagé. Une Task always_run attend la fin de tous ses prérequis. Pour les autres Tasks, Lancelot vérifie les erreurs non ignorées des prérequis, puis l’arrêt global, puis que les prérequis ont terminé avec succès, avertissement ou erreur ignorée. Une Task autorisée à démarrer doit enfin obtenir une place libre. Une désactivation peut aussi faire passer une Task de BLOCKED à DEACTIVATED.
